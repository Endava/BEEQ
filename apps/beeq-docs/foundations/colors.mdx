Color in BEEQ serves communication, not decoration. The system gives every color a clear role — brand identity, feedback, hierarchy, or data — so interfaces stay consistent across products and themes.

<Note>
  Always reach for a **mode role** (`--bq-text--primary`, `--bq-ui--brand`, etc.) rather than a raw primitive value. Mode roles adapt automatically to the active theme and to light and dark mode. Primitives do not.
</Note>

## Color architecture

BEEQ resolves every color through four layers. Each layer only references the layer above it, so a change at the top flows through every role, component, and mode below.

| Layer | Examples | Defined per | What it's for |
|---|---|---|---|
| **1. Primitives** | `--bq-iris-600`, `--bq-grey-800`, `--bq-endava-orange-600` | Palette | Raw hex values. Pick from them when you define a theme. |
| **2. Root semantics** | `--bq-brand`, `--bq-brand-strong`, `--bq-info`, `--bq-neutral-800`, `--bq-white`, `--bq-black` | Theme (`bq-theme`) | The theme's intents and neutrals. Change these to rebrand. |
| **3. Mode roles** | `--bq-background--primary`, `--bq-text--brand`, `--bq-ui--brand`, `--bq-text--on-brand`, `--bq-focus` | Theme × mode (`bq-mode`) | What you style UI with. Each role maps to a root semantic and flips between light and dark. |
| **4. Component variables** | `--bq-button--primary-background`, `--bq-alert--background-info` | Component | Per-component hooks. Each defaults to a mode role. |

For example, the primary button fill in the BEEQ theme resolves like this:

```text
--bq-iris-600 → --bq-brand → --bq-ui--brand → --bq-button--primary-background → <bq-button>
```

BEEQ components only read mode roles and component variables — never primitives or root semantics directly. Mode roles in turn only reference root semantics, which is why rebranding the root layer is enough to restyle every component in both modes.

## Color palette

The palette on this page is the **root semantics** layer — the colors each theme assigns to its intents, neutrals, and data series. Every color is shown for both built-in themes. To switch themes in your app, see [Themes and modes](/theming/themes-and-modes).

### Intent scale

BEEQ has six intents: **brand**, **accent**, **info**, **success**, **warning**, and **danger**. Every intent ships five steps, and each step has a single job:

| Step | Token | Job | Used by |
|---|---|---|---|
| Light | `--bq-{intent}-light` | Subtle tint in light mode | `--bq-ui--{intent}-alt` |
| Base | `--bq-{intent}` | Solid fill | `--bq-ui--{intent}` |
| Dark | `--bq-{intent}-dark` | Subtle tint in dark mode | `--bq-ui--{intent}-alt` |
| Strong | `--bq-{intent}-strong` | Text, icons, and strokes on light surfaces | `--bq-text--{intent}`, `--bq-icon--{intent}`, `--bq-stroke--{intent}` in light mode |
| Bright | `--bq-{intent}-bright` | Text, icons, and strokes on dark surfaces | `--bq-text--{intent}`, `--bq-icon--{intent}`, `--bq-stroke--{intent}` in dark mode |

The base step is tuned to be recognizable as a fill, not to be readable as text. That's why intent text never uses the base step: `-strong` and `-bright` are the steps that reach **4.5:1** on neutral surfaces and on the matching `-alt` tint. `-bright` also reaches **APCA Lc 60**, because WCAG 2 overrates light text on dark surfaces. When a base color is already dark enough, `-strong` points to the same primitive — the BEEQ brand is one example.

- **Brand** anchors primary actions, selection, and brand surfaces.
- **Accent** is a secondary brand color for white-label themes. BEEQ components don't use it; the Endava theme aliases it to brand.
- **Info** communicates neutral, informational feedback. It's a separate intent and never resolves through brand.
- **Success**, **warning**, and **danger** communicate feedback states. Never use them for decoration or branding.

## Mode roles

Mode roles are the building blocks of every BEEQ component. They abstract the "what" (raw hex) from the "why" (intended role), so the same token resolves to the right value for the active theme and mode without manual overrides.

The swatches show the BEEQ theme in the current docs mode — click any swatch to copy the CSS custom property name. The tables list the root semantic each role points to, without the `--bq-` prefix, for both themes and modes.

| Token | Light mode | Dark mode | When to use |
|---|---|---|---|
| `--bq-ui--{intent}` | `{intent}` | `{intent}` — Endava uses `{intent}-bright` for info, success, warning, and danger | Solid fill. Pair with `--bq-text--on-{intent}`. |

`{intent}` is one of `brand`, `accent`, `info`, `success`, `warning`, or `danger`.

### States

State tokens drive hover, pressed, and focus feedback. They're mode roles, so they follow the active theme and mode.

| Token | Value | When to use |
|---|---|---|
| `--bq-hover` | `#444546` | Mixing base for hover states — never painted directly |
| `--bq-active` | `#1f2026` | Mixing base for pressed states — never painted directly |
| `--bq-focus` | `brand-strong` (light), `brand-bright` (dark) | Keyboard focus outlines |

Hover and active colors are derived where they're used, by mixing the rest color with the state base at 20%:

```css
.my-action:hover {
  background-color: color-mix(in srgb, var(--bq-ui--brand), var(--bq-hover) 20%);
}

.my-action:active {
  background-color: color-mix(in srgb, var(--bq-ui--brand), var(--bq-active) 20%);
}
```

BEEQ components work the same way: component variables hold the rest color, and the stylesheet applies the mix. Override the rest color and the hover and active states follow. A `*-hover` component variable only exists when the hover state starts from a different color than the rest state — for example, `--bq-option--background-hover` defaults to `--bq-ui--secondary` — and it holds that base role, not a pre-mixed value.

## Usage rules

Every family has one job. Pairing tokens from the same row keeps contrast within the tested ranges.

| Family | Use it for | Pair it with |
|---|---|---|
| `--bq-background--*` | Page and container surfaces | `--bq-text--primary`, `--bq-text--secondary`, `--bq-text--{intent}`, and the matching icon tokens |
| `--bq-ui--*` | Component fills | Solid `--bq-ui--{intent}` → `--bq-text--on-{intent}`. Tint `--bq-ui--{intent}-alt` → `--bq-text--{intent}`, `--bq-icon--{intent}`, `--bq-stroke--{intent}`. `--bq-ui--inverse` → `--bq-text--inverse`. |
| `--bq-text--*` | Typography | `--bq-text--{intent}` only on neutral surfaces (`primary`, `secondary`) or the matching `-alt` tint — never on a solid fill |
| `--bq-text--on-*` | Text and icons on a solid intent fill | Its own `--bq-ui--{intent}` only. Change both together. |
| `--bq-icon--*` | SVG fills | The same surfaces as text. Needs 3:1. |
| `--bq-stroke--*` | Borders and outlines | `tertiary` for interactive control boundaries (3:1). `primary` is decorative only. `secondary` is for subtle or disabled borders. |
| `--bq-hover`, `--bq-active` | State mixing | `color-mix()` with a rest color only |
| `--bq-focus` | Focus outlines | Any surface. Override it on its own when your brand color is too light to read as an outline. |

    - Put intent text (`--bq-text--brand`) on a solid intent fill

    - Apply feedback colors (success, warning, danger) for decoration or branding
    - Rely on color alone to communicate state or meaning
  </Card>

## Using colors in code

### CSS custom properties

Every token is a native CSS custom property. Apply mode roles directly to any element:

```css
.card {
  background-color: var(--bq-background--primary);
  border: 1px solid var(--bq-stroke--primary);
  color: var(--bq-text--primary);
}

.badge--success {
  background-color: var(--bq-ui--success-alt);
  color: var(--bq-text--success);
}

.tag--brand {
  background-color: var(--bq-ui--brand);
  color: var(--bq-text--on-brand);
}
```

Primitive values are available when you need a specific scale step — for example, building a gradient or a custom illustration:

```css
.hero-gradient {
  background: linear-gradient(
    135deg,
    var(--bq-iris-100),
    var(--bq-iris-600)
  );
}
```

### Tailwind CSS

Add `@beeq/tailwindcss` to your project to use BEEQ's mode roles as Tailwind utility classes.

**Tailwind v3** — add it as a preset in `tailwind.config.ts`:

```ts
import beeqPreset from '@beeq/tailwindcss';
import type { Config } from 'tailwindcss';

export default {
  content: ['./src/**/*.{html,ts,tsx,vue}'],
  presets: [beeqPreset],
  theme: {
    extend: {
      // Add your own utilities on top of BEEQ's token set
    },
  },
} satisfies Config;
```

**Tailwind v4** — load it with `@plugin` in your CSS entry file:

```css
@import "tailwindcss";
@plugin "@beeq/tailwindcss";
```

Once set up, all mode roles are available as utility classes:

| Category | Tailwind prefix | Example class |
|---|---|---|
| Background | `bg-` | `bg-primary`, `bg-brand`, `bg-inverse` |
| Text | `text-` | `text-primary`, `text-secondary`, `text-danger`, `text-info` |
| On-color text | `text-on-*` | `text-on-brand`, `text-on-success`, `text-on-danger` |
| Border | `border-` | `border-tertiary`, `border-brand`, `border-brand-alt` |
| Icon fill | `fill-` | `fill-primary`, `fill-brand`, `fill-success` |
| UI fill | `bg-ui-*` | `bg-ui-brand`, `bg-ui-info`, `bg-ui-danger-alt` |
| Data fill | `bg-data-*` | `bg-data-01`, `bg-data-05` |

Primitive hues are also available as standard Tailwind color utilities:

```html
<!-- Mode roles (recommended) -->
<div class="bg-primary text-primary border border-primary">…</div>
<p class="text-secondary">Supporting text</p>
<span class="text-danger">Error message</span>

<!-- Brand badge: solid fill + its on-color -->
<span class="bg-ui-brand text-on-brand rounded-full px-s py-xs2 text-s font-semibold">
  New
</span>

<!-- Success state: tint + intent text -->
<div class="bg-ui-success-alt border border-success text-success rounded-s p-m">
  Changes saved successfully.
</div>

<!-- Primitive hue (use sparingly — only for custom illustrations or theme overrides) -->
<span class="bg-iris-100 text-iris-800">Custom highlight</span>
```

To apply a custom brand, override the CSS custom properties in your stylesheet — the utility classes resolve to whatever the CSS variables point to. See [Theming and customization](#theming-and-customization) below.

## Accessibility

Color alone must never be the only way information is communicated. Always pair color with text labels, icons, or patterns.

BEEQ's mode roles meet **WCAG 2.1 Level AA** contrast when you pair them as described in [Usage rules](#usage-rules). An automated contrast test resolves every pair below in all four combinations — BEEQ and Endava, light and dark — and fails the build if a pair drops under its minimum.

| Foreground | Surfaces | Minimum |
|---|---|---|
| `--bq-text--primary`, `--bq-text--secondary` | `--bq-background--primary`, `--bq-background--secondary`, `--bq-ui--primary`, `--bq-ui--secondary` | 4.5:1 |
| `--bq-text--{intent}` | The four neutral surfaces above and `--bq-ui--{intent}-alt` | 4.5:1, and APCA Lc 60 in dark mode |
| `--bq-text--inverse` | `--bq-ui--inverse`, `--bq-background--inverse` | 4.5:1 |
| `--bq-text--on-{intent}` | `--bq-ui--{intent}` at rest, hover, and active | 4.5:1 |
| `--bq-icon--primary`, `--bq-icon--secondary`, `--bq-icon--{intent}`, `--bq-stroke--tertiary`, `--bq-stroke--{intent}`, `--bq-focus` | `--bq-background--primary`, `--bq-ui--primary` | 3:1 |
| `--bq-ui--tertiary` | `--bq-ui--primary` | 3:1 |

Some pairs are deliberately outside these guarantees:

- `--bq-stroke--primary` is decorative and `--bq-stroke--secondary` marks subtle or disabled borders, so neither carries the 3:1 non-text requirement. Use `--bq-stroke--tertiary` for borders that identify an interactive control.
- In the Endava theme, `--bq-text--secondary` is only legible on `primary` and `secondary` surfaces. Don't place it on `--bq-background--tertiary` or `--bq-background--alt`.

<Warning>
  **Endava brand fills are a large-text exception.** White on Endava Red Orange (`#FF5640`) is **3.15:1**, so `--bq-text--on-brand` and `--bq-text--on-accent` meet AA only for large text (24px, or 18.66px bold) and non-text UI. Keep labels on Endava brand fills large, or darken the fill for your app:

  ```css
  :root[bq-theme="endava"] {
    --bq-ui--brand: #d63b10;
    --bq-ui--accent: #d63b10;
  }
  ```

  `#D63B10` is the brand-contrast orange used on [endava.com](https://www.endava.com). White text on it reaches 4.67:1 at rest, and more on hover and active. For more contrast, use `var(--bq-brand-strong)` (`#C33600`, 5.46:1).
</Warning>

<Tip>
  Verify custom color pairings with the [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) or the [APCA Contrast Calculator](https://www.myndex.com/APCA/) before shipping. For solid fills, check the hover and active mixes too.
</Tip>

## Theming and customization

<Note>
  **Designers:** need to build a custom palette for a client project before applying it in Figma? See [Building your color palette](/getting-started/for-designers#building-your-color-palette).
</Note>

All BEEQ components read colors from CSS custom properties. Overriding those properties is the **one universal mechanism** for applying a custom brand — no library modifications needed, and it works regardless of your styling tool. BEEQ declares its theme and mode tokens inside `:where()`, so they have zero specificity and any plain selector in your stylesheet wins.

Rebrand at the root layer and set the whole intent scale, plus the on-color for the new fill:

```css
/* your-theme.css */
:root {
  --bq-brand-light: #e0f2fe;
  --bq-brand: #0369a1;
  --bq-brand-dark: #0c4a6e;
  --bq-brand-strong: #0369a1;
  --bq-brand-bright: #7dd3fc;

  --bq-text--on-brand: var(--bq-white);
}
```

If your project also uses Tailwind, adding `@beeq/tailwindcss` makes your own utility classes (`bg-brand`, `text-primary`, etc.) resolve to the same tokens. The two approaches are independent and complementary — the Tailwind integration does not replace CSS overrides, it builds on top of them.

For per-mode, per-section, and per-component overrides, and a contrast checklist for custom brands, see [Custom theme](/theming/custom-theme).
